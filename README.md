# Mutex Job Matrix — Draft / Publish / Effective-Time Versioning

Adds **draft → publish → effective-time versioning** and **immutable historical
snapshots** to the mutual-exclusion job matrix.

At every scheduling or start decision the applicable matrix version **and** the
concrete conflict basis are frozen onto the decision row. Later matrix changes
only affect new decisions whose planned time meets the new effective
conditions — they can never rewrite existing plans, receipts, or audit
conclusions.

## Core guarantees

| Concern | Mechanism |
| --- | --- |
| Frozen version per decision | `plan_decisions.matrix_version_no / matrix_hash / matrix_snapshot` are written in the same transaction as the decision and never updated |
| Conflict basis frozen | `plan_decisions.conflict_basis[]` names the exact rule index, job types and offending job |
| Append-only history | SQLite triggers reject UPDATE/DELETE on `plan_decisions` and on published matrix content |
| Disjoint effective windows | Published versions form half-open windows `[effective_at, superseded_at)`; equal/earlier cutovers are rejected with `OVERLAPPING_EFFECTIVE_WINDOW` |
| Idempotent publish | `idempotency_key` unique; retry returns the same published version (HTTP 200 replay) |
| Idempotent plan submission | plan `idempotency_key` unique; retry replays the original decision |
| Concurrent publish | Each publish runs in an `IMMEDIATE` write transaction; same instant → one winner + unique-index rejection for losers; same key → replays |
| Cross-boundary selection | Version is resolved by **planned_start_at**, not submission time |
| Restart-safe verification | `GET /v1/plans/:id/replay` recomputes from the frozen snapshot, verifies its sha256 and compares bases — all state is in the DB file |

## Version timeline example

```
v1 (baseline/legacy)   [1970-01-01 ──────────── 2026-03-01)
v2 (adds lift|weld)                             [2026-03-01 ── 2026-06-01)
v3                                                             [2026-06-01 ── ∞)
```

A February plan is forever judged by v1; an April plan is judged by v2.


Environment: `MATRIX_DB_PATH` (default `./data/matrix.db`), `PORT`.

## API summary

- `POST   /v1/matrix/drafts` — create draft
- `PUT    /v1/matrix/drafts/:id` — edit draft
- `POST   /v1/matrix/drafts/:id/publish` — publish at `effective_at` (requires `idempotency_key`)
- `GET    /v1/matrix/versions[/current|/:id]` — published snapshots
- `POST   /v1/plans` — schedule/start; freezes version + basis (conflicts recorded with HTTP 409)
- `GET    /v1/plans/:id/replay` — hash verification + basis recomputation
- `GET    /v1/audit/events` — lifecycle/decision audit trail

## Legacy migration

When an old database contains `legacy_mutex_matrix` (flat resource/type pairs)
and `legacy_job_plans`, migration 003:

1. groups pairs into rules and publishes them as **version 1 effective at the
   epoch**, so every historical moment resolves to v1;
2. replays legacy plans chronologically against v1 using the same conflict
   engine as live planning and stores identical frozen decision rows
   (`client_request_id = "legacy:<id>"`);
3. is idempotent and never runs again once a published version exists.

With no legacy tables, a built-in baseline matrix is published as v1.

## Acceptance mapping

- *Old plans always replay under v1* — `test/replay-restart.test.mjs`, `test/plans.test.mjs`
- *New plans after v2 judged by v2* — same files; new `lift|weld` rule only applies post-cutover
- *Overlapping windows rejected* — `test/versioning.test.mjs`
- *Retry of same publish is idempotent* — `test/versioning.test.mjs`, `test/concurrency.test.mjs` (6-way same-key race)
- *Concurrent publish has one valid result* — `test/concurrency.test.mjs` (real OS processes)
- *After restart, conflict reason + snapshot verifiable* — `test/replay-restart.test.mjs` (fresh process, later v3 published in between)
